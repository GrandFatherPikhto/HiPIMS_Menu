# HiPIMS_Menu

Прошивка STM32F103C8T6 ("Blue Pill"), реализующая интерфейс оператора (меню
на LCD1602, поворотный энкодер EC11) для HIPIMS-генератора импульсов, чьё
таймингово-критичное ядро работает на отдельной ПЛИС. Эта прошивка — SPI
master; ПЛИС — SPI slave и единственное, что реально генерирует импульсы.

Проект ПЛИС живёт в отдельном репозитории, `HIPIMS_Generator`
(Quartus/VHDL, EP4CE6E22C8 / Cyclone IV E). Этот репозиторий не содержит и
не отслеживает VHDL — он только реализует протокол, который ПЛИС ожидает.

English version: [README.md](README.md).

## Почему UI на STM32, а не на ПЛИС

Меню, драйвер LCD и обработка энкодера изначально были реализованы прямо на
VHDL на ПЛИС. Эта версия работала и была таймингово чистой, но съедала 54%
логики устройства (3363/6272 LE) и оказалась слишком сложной, чтобы
владелец проекта мог сам её поддерживать и дорабатывать. Перенос UI с ПЛИС
на дешёвый STM32 в роли SPI-мастера снизил загрузку ПЛИС до ~32% (1996 LE) и
улучшил запас по таймингам с ~1нс до 11.4нс. Теперь ПЛИС "тупая": держит
только таймингово-критичное ядро генерации импульсов и SPI-регистровый файл.
Это решение окончательное — откатывать его не нужно.

## Железо

- **STM32F103C8T6 "Blue Pill"** — голый чип, без Wi-Fi. 72МГц (HSE 8МГц ×
  PLL9), APB1=36МГц, APB2=72МГц.
- **LCD1602** через переходник **PCF8574** по I2C (адрес `0x27`), питание
  5В.
- **Энкодер EC11 с кнопкой** для навигации по меню и редактирования
  значений.
- **Связь с ПЛИС**: SPI, STM32 — мастер, EP4CE6E22C8 — слейв.
- **Fault LED**: загорается, когда анодный канал сообщает о живой
  неисправности.
- **Отладочный UART** (USART1): TX-only диагностическая консоль, добавлена
  для живой отладки на столе. См. [Отладочный UART](#отладочный-uart-временно)
  ниже — она явно временная, не постоянная часть прошивки.
- ST7789/240x320 — отложенная опция, не реализована.

## Программный стек

- PlatformIO, `board = bluepill_f103c8`, `framework = stm32cube`.
- **Только LL (Low-Layer) драйверы ST** — без HAL, без Arduino/STM32duino.
  Это явный, не подлежащий обсуждению выбор владельца проекта: прямой доступ
  к регистрам через именованные LL-функции/макросы, без скрытой магии
  HAL-абстракции.
- `build_flags = -DUSE_FULL_LL_DRIVER` обязателен, чтобы получить
  высокоуровневые LL-структуры `*_InitTypeDef` (`LL_SPI_InitTypeDef`,
  `LL_I2C_InitTypeDef`, `LL_TIM_ENCODER_InitTypeDef`, `LL_USART_InitTypeDef`)
  — без него доступны только inline-хелперы для отдельных битов регистров.
- Прошивка/отладка через CMSIS-DAP: `upload_protocol = cmsis-dap`,
  `debug_tool = cmsis-dap` (дефолт платы — stlink, которым этот пробник не
  является).

Стиль кода везде в проекте: простой, плоский, читаемый C. Без преждевременных
абстракций, без фреймворка под конечный автомат меню — именно такая
сложность и сделала старое VHDL-меню неподдерживаемым, и весь смысл
переписывания был в том, чтобы не повторить эту ошибку.

## Распиновка

Согласовано с владельцем проекта 2026-08-18. Нигде не нужен AFIO remap —
везде дефолтный маппинг периферии.

### SPI1 → ПЛИС (`HIPIMS_Generator`)

| Пин | Функция |
|-----|---------|
| PA4 | CS_N — программный GPIO (не аппаратный NSS; держится low на всю многобайтную транзакцию) |
| PA5 | SCK |
| PA6 | MISO — ПЛИС гонит сюда статус/ACK-байт (протокол v2) |
| PA7 | MOSI |

### I2C1 → LCD1602 (через PCF8574)

| Пин | Функция |
|-----|---------|
| PB6 | SCL |
| PB7 | SDA |

LCD1602 + PCF8574 питаются от 5В; PB6/PB7 — 5V-tolerant (FT) пины,
настроены как open-drain, подтяжки уже есть на плате PCF8574.

### Энкодер EC11

| Пин | Функция |
|-----|---------|
| PA0 | TIM2_CH1 = канал A энкодера |
| PA1 | TIM2_CH2 = канал B энкодера |
| PA2 | кнопка энкодера (GPIO, pull-up, кнопка на GND) |

A/B заведены на TIM2 специально ради аппаратного **Encoder Mode**
(`LL_TIM_ENCODERMODE_X4_TI12`) — таймер сам считает квадратурные фронты в
железе (регистр `CNT`), без прерывания на каждый фронт. Прошивка просто
периодически опрашивает разницу.

### Индикация неисправности

| Пин | Функция |
|-----|---------|
| PB0 | выход, высокий уровень, если `fault_a_live` или `fault_b_live` |

### Отладочный UART (USART1) — временно

| Пин  | Функция |
|------|---------|
| PA9  | TX, 115200 8N1 |
| PA10 | RX — разведён, но прошивкой не читается (только вывод) |

### Свободно / зарезервировано

PA3, PB1, PB3–5, PB8–15, PC13–15 свободны под будущее (например, ST7789 —
не начинать без явной просьбы). PA13/PA14 — это SWD, трогать нельзя.

## SPI-протокол v2

Полный дуплекс, Mode 0 (CPOL=0, CPHA=0), MSB first, `CS_N` управляется
прошивкой вручную и держится low на всю пачку кадров.

Единица обмена — **7 байт**:

| Байт | Содержимое |
|------|------------|
| 0 | адрес регистра, `0..NUM_REGS-1` |
| 1–4 | 32-битное знаковое значение, big-endian |
| 5 | CRC-8 по байтам 0–4 |
| 6 | мастер шлёт байт-пустышку и одновременно принимает статус-байт по MISO |

CRC-8: полином `x^8+x^2+x^1+1` (`0x07`), init `0x00`, без рефлексии
входа/выхода, без финального XOR — вариант SMBus PEC. Реализовано
побайтово в `hipims_crc8()` (`src/hipims_spi.c`), численно проверено на
идентичность побитовой VHDL-реализации на ПЛИС.

Статус-байт (читается на байте 6):

| Бит | Значение |
|-----|----------|
| 0 | ACK — 1, если CRC совпал и (если адрес был в диапазоне) запись прошла |
| 1 | `fault_a` живой — не привязан к текущей транзакции |
| 2 | `fault_b` живой |
| 3–7 | резерв, 0 |

### Ретраи и глитч-фильтр ПЛИС

На стороне ПЛИС на `SCK`/`MOSI`/`CS_N` стоит глитч-фильтр, отбрасывающий
любой фронт короче 4 тактов ПЛИС (80нс @ 50МГц) — добавлен после того, как
реальная силовая коммутация анодного канала на живом железе поймала
заметную наводку на SPI-линиях. Это накладывает два обязательных правила на
схему ретраев:

1. **Никогда не слать 7-байтную единицу повторно под тем же `CS_N low`.**
   Если помеха воткнула лишний фронт в `SCK`, счётчик бит/байт на ПЛИС
   сбивается, а сбрасывается он только по `CS_N` high. Повторная посылка в
   той же сессии — это NACK за NACK-ом. Правильно: `CS_N` high → пауза →
   `CS_N` low → заново все 7 байт.
2. **Импульс `CS_N` high между ретраями должен быть заметно длиннее 80нс.**
   Два подряд идущих GPIO-регистровых вызова на 72МГц могут уложиться в
   ~30-60нс — глитч-фильтр отфильтрует их как помеху, и ретрай окажется
   невидим для ПЛИС. `hipims_spi_cs_gap_delay()` вставляет явную задержку
   (~200 итераций busy-loop) между попытками.

`hipims_spi_write_reg()` повторяет попытку до `HIPIMS_SPI_MAX_RETRIES` (10)
раз на NACK, после чего сдаётся и возвращает `false`. ПЛИС сама ничего не
ретраит.

## Карта регистров

`spi_regs_pkg.vhd` на стороне ПЛИС, адреса 0-based, `NUM_REGS = 36`. Все
регистры времени/ширины/задержки/периода — **сырые такты ПЛИС 50МГц** (1
LSB = 20нс), никогда не микросекунды и не миллисекунды — перевод в
человеческие единицы полностью на стороне STM32 (`raw_cycles = us * 50`).

```
REG_ENABLE      = 0   -- 0/1, глобальный разрешающий флаг генерации
REG_START       = 1   -- 0/1, физический "разрешительный" пин, не связан с ENABLE
REG_PERIOD      = 2   -- период, сырые такты
REG_LEGA_WIDTH  = 3   -- ширина импульса плеча A, сырые такты
REG_LEGB_ENABLE = 4   -- 0/1, плечо B (пока физически не разведено)
REG_LEGB_DELAY  = 5   -- знаковая задержка плеча B от старта плеча A, сырые такты
REG_LEGB_WIDTH  = 6   -- ширина импульса плеча B, сырые такты
REG_CH_BASE     = 7   -- 8 probe-каналов (i=0..7): enable=+i*3, delay=+i*3+1 (знак.), width=+i*3+2

-- Анодный канал (половина-мост на SiC с обвязкой fault/reset, добавлено
-- 2026-08-18), стартует синхронно от того же события, что и плечо A:
REG_ANODE_ENABLE   = 31  -- 0/1, master on/off анодного канала
REG_ANODE_PERIOD   = 32  -- период ШИМ анодной пачки, сырые такты
REG_ANODE_DELAY    = 33  -- знаковая задержка начала пачки от общего старта, сырые такты
REG_ANODE_DURATION = 34  -- длительность пачки, сырые такты
REG_ANODE_DEADTIME = 35  -- ДОБАВКА deadtime поверх зашитого пола 300нс, сырые такты,
                         --   БЕЗ ЗНАКА. Не абсолютное значение — 0 значит
                         --   "только пол, без добавки". ПЛИС насыщает
                         --   итоговый deadtime до диапазона [300нс, 100мкс]
                         --   независимо от присланного значения.

NUM_REGS = 36
```

`*_ENABLE`-регистры: `=1` → true, всё остальное → false.

### Ограничения диапазона

- `TIME_WIDTH = 23` бита → `0 .. 8 388 607` сырых тактов (~167.77мс) —
  потолок для `period`/`leg_a_width`/`leg_b_width`/`anode_duration`/`anode_period`.
- `MAX_PERIOD_CYCLES = 8 338 607` тактов (~166.77мс) — безопасный максимум
  именно для `REG_PERIOD`, с запасом 25000 тактов (500мкс) с каждой стороны
  окна.
- Знаковые задержки (`REG_LEGB_DELAY`, `delay` probe-каналов,
  `REG_ANODE_DELAY`) — от `-25000` тактов (-500мкс) до `period + 25000`
  тактов. ПЛИС их не валидирует и не зажимает — это делает прошивка в
  `menu_reg_limits()` перед отправкой.
- `REG_ANODE_DEADTIME` редактируется на STM32 в отдельном, гораздо более
  узком UI-диапазоне (см. ниже) — насыщение ПЛИС до [300нс, 100мкс] это
  отдельная, независимая защита.

## Меню / интерфейс

`hipims_menu.c` рисует плоский список из 37 пунктов на LCD 16×2: 36 реальных
регистров плюс два UI-пункта (`STEP`, `ERRORS`). Вращение энкодера двигает
выбор либо, во время редактирования, меняет значение на текущий шаг; клик
кнопкой входит в режим редактирования / подтверждает его.

- **STEP** — задаёт шаг редактирования для всех времязадающих регистров
  (`20нс / 1мкс / 10мкс / 100мкс / 1мс`). Отдельный пункт меню, а не
  константа, потому что подбирать грубый регистр (период, диапазон ~мс) и
  тонкий (несколько сотен нс) одним и тем же шагом непрактично. Хранится
  только в RAM, не сохраняется во флеш.
- **ERRORS** — показывает `A: OK/FLT  B: OK/FLT` из живых бит fault в
  статус-байте. Клик по нему **не** входит в редактирование — он запускает
  ручной сброс неисправности (см. ниже).
- Каждый реальный регистр отображается как `мкс.ннн` (только целые числа,
  без float — 3 знака после запятой микросекунды это ровно наносекунда, и 1
  сырой такт всегда делится нацело на целые наносекунды), кроме:
  - `ENABLE`/`START`/`LEGB_ENABLE`/`ANODE_ENABLE`/`ENABLE` probe-каналов —
    отображаются просто как `0`/`1`.
  - `ANODE_DEADTIME` — отображается как целое число наносекунд (например,
    `300ns`), потому что формат `мкс.ннн` для таких маленьких значений
    читается плохо. У него также свой **фиксированный шаг редактирования
    20нс (1 сырой такт) и отдельный клэмп 0–2000нс**, независимый от
    глобального STEP — глобальный шаг в масштабе микросекунд пролетел бы
    весь рабочий диапазон этого регистра за один клик. Потолок в 2000нс
    выбран сознательно с запасом выше "классических" ~1мкс deadtime для
    более медленной кремниевой обвязки (IR-класс MOSFET/драйвер) —
    конкретное железо макета ещё не зафиксировано; SiC с быстрыми
    драйверами (класса UCC21750) обычно требует заметно меньше, ближе к
    зашитому полу ПЛИС в 300нс.
- По подтверждению редактирования значение пишется во флеш (`storage_set`)
  и отправляется по SPI (`hipims_spi_write_reg`). Если запись по SPI не
  прошла после всех ретраев, на LCD ~800мс показывается `SPI FAIL`.
- При старте (`menu_init`) все сохранённые значения регистров заново
  отправляются на ПЛИС, и та же полная рассылка повторяется каждые ~1.5с из
  `menu_tick()` (`menu_resend_all_regs()`). У ПЛИС нет энергонезависимой
  памяти под регистры — отдельная переконфигурация ПЛИС (перезаливка через
  Programmer, или power-cycle только платы ПЛИС) молча обнуляет все 36
  регистров, а STM32 об этом не узнаёт, потому что видел их только один раз
  при собственном старте. Без периодической рассылки это выглядит как "SPI
  работает (ACK приходит), но генерации нет" и ловится долго вслепую —
  найдено на bring-up 2026-08-19. Слать по таймеру безопасно: `REG_ENABLE`
  снимает fault-защёлку анодного канала только по фронту `0→1`, а не по
  уровню, так что повторная отправка того же `1` не вызывает рестарт;
  остальные регистры — чистые уровни, повторная запись текущего значения
  не имеет побочных эффектов.

## Обработка неисправностей — только ручной сброс

**Политика, явно заданная владельцем проекта и зашитая в дизайн ПЛИС: после
неисправности генерация должна прекратиться, а её перезапуск — всегда явное
действие, инициированное STM32, никогда не автоматическое.**

Это заменило собой более раннюю схему автосброса, которая была реализована
и затем полностью выброшена, когда прояснилось реальное ограничение:
защёлка неисправности на ПЛИС раньше снималась сама после cooldown ~102мкс,
но STM32 узнаёт о неисправности по SPI на порядки медленнее — так что
генератор мог незаметно перезапуститься ещё до того, как прошивка вообще
узнала о неисправности. Теперь защёлка сама не снимается; она снимается
**только** по фронту `0→1` на `REG_ENABLE`, который может произвести
только прошивка.

`hipims_fault_tick()` опрашивает раз в ~200мс (каждый 20-й тик из 10мс
главного цикла), перезаписывая `REG_START` тем же значением — исключительно
чтобы получить свежий статус-байт. Намеренно не `REG_ENABLE`, чтобы обычный
опрос никогда случайно не произвёл фронт, снимающий защёлку. Биты
неисправности читаются из статус-байта **безусловно**, независимо от того,
подтвердилась ли эта конкретная запись ACK-ом — по спецификации биты fault
валидны в любом случае, и более ранний баг (исправлен) отбрасывал их при
NACK.

`hipims_fault_reset()`, запускаемый кликом по пункту меню `ERRORS`, пишет
`REG_ENABLE=0`, ждёт 1мс, затем пишет `REG_ENABLE=1`. Если физическая
причина неисправности ещё не устранена, защёлка немедленно срабатывает
заново, и `fault_a`/`fault_b` появляются снова на следующем опросе — это
ожидаемо, не баг.

## Хранение во флеш / wear-leveling

Значения регистров переживают цикл питания в последней 1KB странице флеша
(`0x0800FC00`, страница 63 из 64), в виде append-only лога 6-байтных
записей (`value_lo`, `value_hi`, `addr` — пишется последним, так что потеря
питания посреди записи оставляет запись, которая при чтении просто выглядит
пустой, а не битой). `storage_set()` ничего не делает, если значение
реально не изменилось, и вызывается ровно один раз на законченное
редактирование (клик кнопкой), никогда на каждый тик энкодера — ресурс
стирания страницы флеша (~10000 циклов) реальное, а не теоретическое
ограничение. Лог компактится (стирание + перезапись всех 36 текущих
значений) только когда заполняется страница (~170 записей).

## Отладочный UART (временно)

Добавлен, когда для живой отладки на столе понадобилась диагностика,
которую одним осциллографом не получить. USART1, только TX, LL-реализация
на поллинге (без printf/retarget). На каждую попытку SPI печатается строка:

```
SPI tx#00 addr=01 val=00000001 crc=65 status=01 ACK
```

Смотреть через `pio device monitor` (`monitor_speed = 115200` уже в
`platformio.ini` — отдельный терминал не нужен). Эта консоль реально
помогла диагностировать настоящий таймингово-баг в VHDL на стороне ПЛИС
(см. ниже) и здесь явно помечена как временная инфраструктура, а не
постоянная часть прошивки.

## Статус

Полная цепочка проверена на живом железе (2026-08-18): энкодер → меню → SPI
v2 (CRC + ACK, успех с первой попытки, ретраи не нужны) → коммит регистра на
ПЛИС → реальная генерация импульсов, подтверждено осциллографом для плеч
A/B и для анодного канала (пачка стартует после `ANODE_DELAY`, управляется
`ANODE_ENABLE`/`ANODE_DURATION`), включая видимый зазор deadtime между
плечом A и плечом B.

По пути был найден и исправлен реальный баг на стороне ПЛИС: SPI-записи
детерминированно давали NACK, хотя CRC-8 была независимо проверена
(численно, побайтовая C-реализация против побитовой VHDL) как корректная.
Ручная прогонка тактов синхронной логики VHDL (без симуляции, без
логического анализатора) показала, что `spi_slave_regs.vhd` сдвигал
статус-байт на один лишний бит влево ещё до первого сэмпла байта 6 мастером
— так что реальный бит ACK попадал туда, где мастер читает `fault_a`.
Задокументировано и передано в репозиторий ПЛИС
(`HIPIMS_Generator/techdocs/notes/2026-08-18-status-byte-shift-bug.md`), а
не исправлено прямо здесь, поскольку VHDL — отдельный проект; однострочный
фикс (условие `and bit_cnt /= 0` на сдвиге) применён там и подтверждён
работающим на живом железе.

Ещё не проверено на живом железе: 8 probe-каналов по отдельности (пункты
меню есть, регистры разведены, но не тестировались с реальной пробной
нагрузкой).
